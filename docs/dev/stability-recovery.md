# Fork 日常稳定性优化

## 1. 目标与工作边界

以 [稳定性审查](../reviews/archive/stability-recovery-2026-10-20.md) 为依据，提高日常常驻、断连与恢复的可用性。目标仓库为 `KaniuBillows/vigil-watt`（本机 remote `fork`），原仓库 remote `origin` 只作为来源背景；用户现已授权提交并推送本轮优化到 fork 同名分支；不改已有 PR、不修改 remote、不上传 Release 或试用包。

当前工作分支 `codex/daily-stability-recovery` 从 `5a245f9` 创建。该基线在原本地分支保存贴片左右位置和审查报告；本轮优化按用户授权合成一个提交，推送至 fork 的 `codex/daily-stability-recovery`，便于独立审阅。

不扩展设备型号，不增加硬件命令，不改变现有插件授权、熔断及退避。沿用审查报告的罗技排除范围。UI 新鲜度的原布局文字方案已获用户确认；不以关闭系统电源管理掩盖恢复缺口。

## 3. 蓝牙监视器生命周期

`WatcherRecovery` 保持纯 .NET：工厂创建 `IWatcherSession`，`TimeProvider` 提供可注入的一次性计时器，`WinRtWatcherSession` 才依赖真实 `DeviceWatcher`。两个蓝牙 watcher 都复用该控制器。

- 真正启动成功才记为运行。创建或启动失败自动按 1/3/10/30 秒退避，之后以 30 秒封顶；健康运行至少 2 分钟后发生停止，恢复退避重新从 1 秒开始。
- 异常 `Stopped` 解绑并废弃旧会话，再安排一次重建。启动中途失败但旧会话仍在运行或停止中时，先请求停止；终态未确认前只检查旧会话，不创建替代会话。
- 每个事件携带来源会话，只有当前会话能修改状态。重复 `Start` 不重复订阅；退出先禁止回调、清理重试计时器，主动停止完成后解绑事件，不会自动重启。
- 不能确认旧会话终态时保持隔离并记录错误，不假设 `Stop` 返回就等于全部回调结束。若驱动始终不结束，本批不会强建第二个 watcher；这是需要真机检查的边界。

WinRT 的终态和停止规则依据 [DeviceWatcher 文档](https://learn.microsoft.com/en-us/uwp/api/windows.devices.enumeration.devicewatcher?view=winrt-26100)；退避是本项目策略，不是系统恢复时延承诺。

## 4. 连接代次与快照

`ConnectionEpochs` 为每设备保存单调代次和最近连接证据；设备 ID 比较忽略大小写。移除/重建清条目但不重置全局代次，因此同 ID 再出现不会复用旧令牌。缺失 `IsConnected` 的增量事件沿用已有连接证据，不能把明确离线改回在线。

GATT 发起前捕获代次，在等待串行闸门后和最终提交前复核。经典蓝牙连接确认同样捕获代次；移除、断连、重建或退出后，即使原生操作后来成功，也不能提交。系统给出新电量时使原有 GATT 令牌失效，避免较早补读覆盖较新电量。

每端点最多一份在途 GATT；断连或重建不会清掉在途计数，旧任务收尾后才允许下一份。经典蓝牙的纯 .NET `ConnectionVerificationQueue` 同样限制每端点一份在途确认，同代次合并增量属性，跨代次只保留最新请求；旧调用完成后再启动最新且仍有效的连接确认。不会在旧原生调用尚未完成时，因反复重连而堆积该端点的后台任务；连接枚举在 8 秒后请求取消。

代次校验、状态修改和事件发布共用同一锁，不能先校验再脱锁发布。字典、可变 `DeviceStatus` 和快照也受此锁保护，通知与 `Snapshot` 均返回 `Clone`，消费者不能改写 watcher 内部状态。真实 I/O 的异步等待不持锁；经典蓝牙原有同步节点查询仍是 CR-72 后续隔离范围。

## 5. GATT 收尾

保留每设备 2 分钟限流，明确断连后等待新连接证据再补读。使用传给 WinRT 的取消令牌，整次读取在 24 秒后请求取消，退出也请求取消；取消失败时仍靠代次校验丢弃旧结果。

`BluetoothLEDevice`、取得的全部 `GattDeviceService` 和 `DataReader` 在读取路径收尾。退出后等全部在途及排队补读完成，才释放串行闸门和退出令牌，避免旧任务 `Release` 已释放的闸门。未收到停止事件的监视器仍保留停止订阅以完成解绑，但无法再发布设备事件。

## 7. HID 失效句柄与退役屏障

`HidIoResult` 分类成功、超时、无数据/不支持、取消、访问冲突、协议错误、其他 I/O 错误及明确句柄失效。Win32 6、1167 和意外已关闭流可使句柄失效；995 取消、5/32 访问冲突、1/87 协议错误和笼统的 31 不自动触发重开。协议解析仍由原插件负责，传输层不能凭没有电量就认定设备离线。

`ReadInputResultAsync` 提供类别，原 `ReadInput/ReadInputAsync` 保留字节或 null 的调用约定。普通超时保留唯一挂起读取，晚到数据仍可被下一次调用取走；异步错误即使发生在外层等待超时后也会记录并锁定句柄。输出等待超时也不等于底层写入结束，旧写未完成时不再启动第二份写入。`GetFeature` 等同步调用也纳入在途计数，不能只跟踪 input。

`IHidIo` 将真实 `HidFileIo` 与故障注入分开，生产与测试使用同一个 `HidDeviceHandle`。失败记录带类别、错误码和计数；错误码在对应原生调用后立即取得，打开失败保留真实 Win32 码，构造流失败也关闭已打开的句柄。

基类看到失效句柄后立即推送保留电量的离线副本，并请求恢复调度。扫描不再因为路径还在就复用坏句柄：先禁止旧设备发布、取消监听并关闭句柄，等待 `Drained` 与整个监听任务完成后才释放认领和允许新探测。失败的探测和同身份重复接口也走此路径，不能因为探测已经返回就假定旧 I/O 已退出；等待期间同插件的其他新接口探测也暂停，防止通过别名重建同一物理会话。已有健康设备仍保留。

重开沿用原 `IsCandidate/Probe/BuildDeviceId`。具备可信设备身份的插件可以分辨换接收器；默认路径 ID 仍不能证明物理同一性，CR-83 未解决。Haute 删除独立的立即替换句柄路径，统一重新检查原固件/状态/芯片 ID。不能把这项变化解释为所有设备已获得芯片身份。

同路径重开采用 1/3/10/30 秒封顶退避，取值至少为原协议 `ResolveProbeCooldown`；普通非快速发现的写入插件，重复恢复间隔至少 60 秒。写入型探测必须仍有用户授权，已有熔断未到期不允许恢复握手。相同可信 ID 的替代会话保留熔断档位、最近旁路时刻和读数过滤器，不能用重新探测播种异常电量来绕过过滤。恢复成功后至少健康 2 分钟才重置恢复档位，故障后等待收尾不计为健康；已消失路径的恢复缓存会清理。

只有实际发过帧才计查询失败；空读、写入未授权和纯被动协议不替代插件自身的失败记账。退役结果不得再解除熔断或应用读数。状态修改与快照发布受 `StateGate` 保护，硬件操作仍使用原 `IoGate`，收尾不等待取得正在执行原生调用的 `IoGate`。

关闭失败或旧操作始终不退出时保持隔离，记录故障，不再开新会话。这是安全降级，不是“挂死驱动已经恢复”；同一插件内的轮次仍可能被同步调用阻塞；其他来源由 §10 隔离，CR-72 保留同品牌细化边界。

## 8. 系统恢复信号与有限调度

`SystemRecoveryNotifications` 复用托盘现有隐藏顶层窗口，即使托盘图标关闭也存在。不新增窗口线程，不依赖主窗口是否可见。注册电源恢复、当前会话通知和 HID 接口类的插拔；只接受恢复、解锁及 HID arrival/removal。锁屏本身不清设备、不停止常驻监控，其他设备类和泛化 PnP 变更不会触发恢复。注册失败有日志并使用同一个纯调度器做有限重试，已经成功的注册不会重复申请；失败时普通监控节拍仍保留。

窗口回调只解析信号和排请求，不扫描、不执行 HID I/O。`RecoveryScheduler` 从首个信号开始，以 1/3/10/30 秒为绝对阶段；同窗口内的新信号合并原因且不延后时间。每次等待前一轮完成，慢轮次跨过的阶段直接跳过，不并发补跑。睡眠跨过旧窗口后，新信号建立新代次；已经排队的旧计时器不能取消或执行新代次的检查。在途轮次超过旧窗口时，只保留一个后续新窗口，避免无限积累恢复任务。

`DeviceManager` 将健康检查交给 §10 的插件所有者，从不在超时后并发复用插件。两个蓝牙 watcher 只调用幂等 `Start`，不强停健康 watcher。HID 只对基类插件执行恢复；普通写入型插件的新接口仍等正常轮询，零写入/原已获准快速发现的插件沿用各自能力和冷却。健康已认领接口直接返回，不重新握手。

当前只让显式声明的 Haute 执行额外纯读取健康检查；不把所有插件 `Poll` 搬进四个阶段，避免提高查询写入或离线失败计数频率。其他协议通过已有被动读或常规轮询发现错误后请求恢复。1/3/10/30 是检查阶段，不是设备恢复耗时承诺。

退出先禁用恢复调度并解绑通知，管理器拒绝新轮次/上报，基类插件先禁止新 I/O 并关闭登记过的探测/已认领句柄。字典清理分别等待该插件在途轮次退出后串行执行，认领等待真实 I/O 与监听收尾再释放，不能在活动探测期间并发清字典。现有退出入口仍会结束进程；无法返回的原生调用或失败的关闭不能被宣称为已经优雅收尾。

API 依据：[电源消息](https://learn.microsoft.com/en-us/windows/win32/power/wm-powerbroadcast)、[电源通知注册](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registersuspendresumenotification)、[会话注册与解绑](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsregistersessionnotification)、[设备通知注册](https://learn.microsoft.com/en-us/windows/win32/devio/registering-for-device-notification)。消息不能区分实际睡眠模式，Modern Standby 必须单独验收。

## 10. 插件与数据源隔离（第三批）

移除全局 `_passGate` 与“全部 Attach 完成再逐个 Poll”的屏障。每个插件、HID 扫描、BLE、经典蓝牙及系统电池分别持有一个 `MonitorWorkSlot`；完成一个来源即发布该来源结果，不等其他来源。正常刷新最多观察 8 秒，HID 清单最多观察 2 秒。这里的超时只结束等待，不表示原生任务已取消；旧任务一直由原 slot 持有，发现、轮询和恢复复用它，不排队无限补跑、不新建同一插件会话。

扫描未成功完成时不拿旧清单做 Attach（避免据过期清单错误退役）；已有设备仍可 Poll，蓝牙与系统电池独立运行。扫描卡在单个驱动时，新设备发现仍会降级。恢复也有限等待新清单，避免每次阶段都因扫描尚未完成而跳过重探。设置变化使旧轮次的显式结果失效，禁用来源的后续推送也拒收；退出分别等待各插件旧任务，再清字典和认领。设备集合存储快照，展示与事件也交付副本；较早的状态快照不能覆盖已接收的较晚状态。

隔离粒度是插件及来源，**同一品牌插件内部的单设备阻塞仍会拖住该品牌**，尤其同步 feature 调用不能假设有可靠取消。当前没有把任意 `PollDevice` 并发化，以免越过插件内部状态与会话所有权；CR-72 保持 doing。经典蓝牙的同步节点查询也只隔离在其来源内，不能宣称底层驱动挂死已经恢复。

## 11. 读数新鲜度与保守身份边界

`BatteryObservedAt` 只由成功采信的电量观察推进；`ConnectionObservedAt` 记录连接证据，`StateChangedAt` 记录可见状态变化，`LastUpdated` 保留状态快照时间。离线时撤销 `ReadingConnectionConfirmed`，保留旧值与旧读数时间；重新在线但尚无新电量时不能恢复当前连接的确认。异常过滤不推进读数时间，同值的成功读数会推进；被动同值上报最多每 30 秒更新展示，避免高频帧造成 UI 和数据库负担。

有效期为 5 分钟；过期或重连待确认时保留缓存百分比，在设备行和托盘菜单的现有文字区域提示“读数已过期 / Reading stale”，暂停低电量提醒和剩余时间估算。常规轮次会刷新展示，实际文字切换最多再等一个普通刷新节拍。历史采样按电量观察时间写入，同一个观察无论被定时器或变化事件使用多少次，只写一次；同值的新观察仍可按原采样节拍记录。写库失败不消耗该观察，保留重试机会。未新增表或改写既有历史。

经典蓝牙节点轮询读到相同缓存值时不推进电量时间，名字/类型更新也不能刷新电量。系统属性的新电量推送作为一次观察；Windows 没有提供这些缓存值的硬件采集时刻，所以观察时间不是硬件采集时间的保证。系统电池刷新则来自本轮电源读取。

CR-83 不作猜测性迁移：Haute 仍用已验证的只读芯片 ID，其他现有插件保留原 ID 格式、设置键和历史归属。同名不合并、路径改变不推断同机、旧路径历史不删除；其他品牌要提供可验证标识及换口/多机对照后才能实现身份连续性。本批没有增加探测命令或读取任意序列号。
