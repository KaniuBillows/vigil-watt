# 蓝牙恢复第一批改动面审查

## 1. 基线与边界声明

基线 `5a245f9`，本地分支 `codex/daily-stability-recovery`，面向用户 Fork。原有贴片改动与审查文档已按用户要求单独保存在一个本地提交；本批优化未再提交、推送或修改 PR。

仅修改蓝牙监视器及可注入的生命周期/连接代次逻辑，未改 HID 插件、写入授权、设备协议、历史库、UI 或版本号。未启动应用、替换便携版或操作真机电源/蓝牙；编译不会向设备发帧。

## 2. 逐条发现与处理

- CR-80：用 `WatcherRecovery` 替换两个提前置位的 `_started`，创建失败自动重试；真实 WinRT 事件收敛到可解绑的 `WinRtWatcherSession`。异常停止和启动中途失败都经过停止屏障，不并行创建替代会话；主动退出不重启。
- CR-81：用 `ConnectionEpochs` 保护 GATT 及经典蓝牙连接确认，断连、移除、重建和退出均废弃旧结果；代次校验与状态发布在同一锁内完成，快照和通知复制对象。较新的系统电量也会废弃旧 GATT。
- 每端点只允许一份在途 GATT/连接确认，重建不清除在途占位；确认队列合并同代次属性、只保留最新连接请求，旧原生调用结束后才重试，避免快速断连重连不断积累同设备任务。
- R3/R4：可变状态统一在控制器锁内访问；GATT 异步等待脱锁，退出时先失效再取消，待在途补读全部收尾才释放闸门和令牌；旧会话完成停止后解绑事件。
- R5/R8：创建/启动/停止/解绑和事件处理失败有日志，退避与事件错误带计数；控制器和代次代码零 WinRT 依赖，已链接进核心测试项目。R1/R2 的硬件写入路径未改。

## 3. 需要修正或遗漏的部分

本批不等于完成整份恢复报告。CR-78/79 的系统信号、坏 HID 句柄恢复，CR-72 的全局轮次隔离，CR-82/83 的新鲜度及物理身份仍未实施。经典蓝牙原有同步节点扫描仍可能拖住自身事件与共享轮询；本批不声称消除了该阻塞风险。

监视器失败时保留现有设备快照，不伪造全部设备断连；如何让用户识别缓存/监控停滞仍属于 CR-82。没有新连接证据时不再用旧缓存自行恢复在线，是 CR-81 的保守取舍。

## 4. 未能证实的部分与验证

.NET 8 SDK 8.0.426 的 `dotnet build VigilWatt.sln -c Debug --no-restore --warnaserror` 编译通过，0 警告、0 错误。新增 23 项回归用例已编译，包括模拟 100 次异常重建和 100 次同 ID 断连重连。按仓库约定未执行本地自动测试；本批没有推送，因此 CI 尚未运行。

用例验证的对象是实际生产控制器与代次实现，不能替代 WinRT 适配器的真实事件时序、取消响应、蓝牙开关和睡眠恢复。取消请求没有被表述为驱动必然结束的保证。停止长期不结束时不会启动第二份 watcher，仍需真机观察日志及资源变化。
